# Evidence Campaign — 2026-08-17

## Executive summary

This report records a reproducible, local benchmark campaign for the actual
SHPH code paths. It is engineering evidence, not an independent audit and not
evidence of live Internet throughput, DPI evasion, or DDoS capacity.

The supplied benchmark tables were **not** accepted as measured evidence:
their input distributions are not included, their bucket sizes do not match
the current Shroud2 implementation, the cookie description says BLAKE3 while
SHPH currently uses HMAC-SHA256, and the replay result mixes a Python
measurement with an unmeasured Rust projection.

The standalone runner now exposes `--suite evidence`, which measures:

1. 5,000 deterministic synthetic packets for five traffic profiles through
   the current Shroud2 morphology implementation;
2. 50,000 in-memory ML-KEM decapsulation operations against the current
   stateless-cookie and per-source limiter paths; and
3. 500,000 actual `ReplayWindow::new(128)` validations with deterministic
   out-of-order and duplicate events.

## 1. Shroud2 bandwidth overhead matrix

The baseline is payload bytes only. The measured wire value is the serialized
Shroud2 envelope, including its seven-byte envelope header and padding, while
IP/UDP/Ethernet headers are excluded.

Each row contains 5,000 packets generated by a fixed integer mixer. Payload
ranges are:

| Profile | Payload generator | Shroud2 profile |
| --- | --- | --- |
| Bulk | 900–1,400 bytes | `BulkLab` |
| Video | 800–1,400 bytes | `VideoStreamingLab` |
| Web | 32–799 bytes, with every 20th packet 1,000–1,400 bytes | `WebBrowsingLab` |
| VoIP | 24–119 bytes | `LowLatency`, weighted smallest-fit |
| SSH | 1–80 bytes | `LowLatency`, weighted smallest-fit |

The path budget was 1,472 bytes. Results:

| Traffic profile | Raw payload | Shroud2 wire | Extra bytes | Overhead | Distinct wire sizes |
| --- | ---: | ---: | ---: | ---: | ---: |
| Bulk | 5,752,710 | 7,188,877 | 1,436,167 | 24.965% | 110 |
| Video | 5,491,309 | 6,649,600 | 1,158,291 | 21.093% | 3 |
| Web | 2,273,087 | 4,326,592 | 2,053,505 | 90.340% | 5 |
| VoIP | 356,489 | 1,038,464 | 681,975 | 191.303% | 4 |
| SSH | 201,240 | 1,052,032 | 850,792 | 422.775% | 4 |

The `LowLatency` wire sizes are `128|256|512|1024`, selected with weights
`65|25|8|2`. Web uses `384|768|1024|1280|1472` on this path, with the
`1536` class capped to the negotiated 1,472-byte limit; video uses
`1024|1280|1472`, with larger profile classes capped likewise. In both cases
the weights are `45|30|15|8|2`, after ineligible classes are removed and
classes above the path limit are folded into the path-limit bucket. Compared
with the previous uniform selection, web overhead falls from 125.475% to
90.340% and video from 24.665% to 21.093%. The earlier LowLatency change
reduces VoIP overhead from 791.109% to 191.303% and SSH overhead from
1,500.064% to 422.775%. The SSH result remains high because a 128-byte
minimum wire class is still much larger than a 1–80-byte interactive payload.
These values replace, rather than validate, the supplied table, and they do
not establish browser similarity or DPI classifier failure.

## 2. Pre-authentication CPU comparison

This is an in-memory CPU comparison using 50,000 operations. It is not a
socket flood, spoofed-source test, listener saturation test, or DDoS-capacity
measurement.

| Path | Elapsed | Operations/sec | Result |
| --- | ---: | ---: | --- |
| Direct ML-KEM-768 decapsulation | 3,466 ms | 14,425.072 | 50,000 decapsulations |
| Stateless cookie gate | 86 ms | 575,619.078 | 50,000 issue + forged-cookie verify operations; 50,000 rejected |
| Per-source limiter | 32 ms | 1,518,455.306 | 8 accepted; 49,992 rejected |

The measured cookie/direct local CPU rate factor was `39.904x` in this run.
That number must not be converted into a network DDoS capacity claim. The
current implementation uses rotating HMAC-SHA256 cookies bound to the peer
address; it does not use BLAKE3 for this path.

The direct ML-KEM row repeatedly decapsulates a correctly sized ciphertext
against one generated keypair. It isolates cryptographic cost; it does not
include TCP accept, parsing, deadlines, scheduling, or the full handshake.

## 3. 128-bit replay-window throughput

The runner processed 500,000 nonces through the actual
`ReplayWindow::new(128)` implementation:

| Packets | Accepted | Rejected | Out-of-order samples | Duplicate replays | Elapsed | Validation rate |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 500,000 | 475,000 | 25,000 | 50,000 | 25,000 | 28 ms | 17,490,222.965 packets/sec |

This is a single-threaded Rust measurement on the stated Windows GNU build.
It is not a Python measurement and does not support an unmeasured claim of
“more than 20 million packets/sec” on another compiler, host, or interface.
It also measures nonce validation only, not AEAD decryption, socket I/O, TUN
forwarding, or line-rate networking.

## Explicit non-claims

This record does not prove:

- DPI blindness, browser/CDN traffic indistinguishability, or censorship
  bypass in Russia, Iran, Turkey, or any other network;
- live 50,000-packet network-flood recovery or DDoS resistance;
- two-host throughput, Internet RTT, packet loss recovery, TUN/Wintun
  performance, or 10/40-Gbps saturation; or
- a Python-to-Rust speedup projection.

Those claims require separately designed native-host or two-host experiments
with published inputs, independent capture, and platform-specific provenance.
